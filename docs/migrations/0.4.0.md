# Migrating to Whitaker 0.4.0

This guide covers the changes introduced in the 0.4.0 release: `whitaker check`
becomes the default linting path, and the `whitaker-installer` library gains
one source-breaking error variant. The standalone installer workflow continues
to work unchanged, and workspace metadata integration is unaffected.

## What changes

### `whitaker check` is the default linting path

The previous default was a two-step sequence: run `whitaker-installer` to
provision the lint suite, then run `whitaker --all` to lint. The root
`whitaker` binary now does both in one command:

```sh
whitaker check
```

The first run provisions whatever is missing — the Dylint dependencies, the
Clippy snapshot, the bootstrap metadata and the lint suite — and then lints the
current package. Later runs reuse that installation. This is the same
installation the standalone installer maintains, so a host provisioned by
`whitaker-installer` needs no second copy.

Arguments after `--` are forwarded to `cargo dylint` unchanged:

```sh
whitaker check -- -p my-crate --all-targets
```

`--no-install` refuses to provision and reports `provision.refused` instead,
which is what a locked-down CI step wants after a separate provisioning step.

The standalone installer remains supported and is still the explicit,
scriptable route. Existing scripts that run `whitaker-installer` and then
`whitaker --all` keep their behaviour; moving to `whitaker check` is a
simplification, not a requirement.

### `InstallerError` gains `InstallLock`

`whitaker-installer`'s `InstallerError` is exhaustive on purpose, so a
downstream exhaustive `match` stops compiling when a variant is added. 0.4.0
adds `InstallerError::InstallLock { path, reason }`, reported when the
installation lock cannot be taken. Losing the lock is a host fault rather than
an installation defect: the installation was never inspected, so nothing about
it is known.

Add the arm beside the existing ones:

```rust
match error {
    // ...
    InstallerError::InstallLock { path, reason } => {
        eprintln!("could not lock {path}: {reason}");
    }
}
```

A wildcard arm is also acceptable where the caller does not need to tell the
variants apart.

### Additive bootstrap API

The installer's bootstrap module now publishes `preflight`,
`preflight_with_cargo`, `run_prepared` and `run_prepared_with_cargo`, plus
`PreparedRun`. They are additions, not changes: `run` and `run_with_options`
keep their signatures and behaviour. Only a successful `preflight` produces a
`PreparedRun`, and `run_prepared` runs only against that value. The
[Developer's Guide](../developers-guide.md#bootstrap-boundary) documents the
contract; no migration is needed.

## Migration checklist

1. Where one default command is wanted, replace `whitaker-installer` followed
   by `whitaker --all` with `whitaker check`.
2. Keep the standalone installer where provisioning must stay explicit. After
   provisioning, `whitaker check --no-install` lints without network access or
   installation.
3. Library consumers: add an `InstallerError::InstallLock` arm, or a wildcard,
   to every exhaustive match.
4. Automation that reads statuses can rely on the `check` contract: `0` linted
   cleanly, `1` lint denial or compile failure, `2` usage error, `3` reserved
   for configuration, `4` provisioning, and `5` host or execution failure. An
   operational outcome also prints `whitaker: error[<key>]:` on standard error,
   which distinguishes it from a `cargo dylint` run that itself exited `3`, `4`
   or `5`.

For the full command reference, see the
[User's Guide](../users-guide.md#whitaker-check). For the installer's internal
boundaries, see the
[Developer's Guide](../developers-guide.md#bootstrap-boundary).
